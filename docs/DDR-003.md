Run on a local Worker (`wrangler dev --local`) with the schema and seed loaded, on 2026-10-20:

| EARS row | Check | Result |
|---|---|---|
| F1-1 | Sign up returns 201 and the session cookie signs the person in (`/api/me` returns them) | Pass |
| F1-2 | Sign up with a taken username in different capitalization returns 409 and creates no account | Pass |
| F2-1 | Creating a trip returns the trip and an invite link; the creator is a member | Pass |
| F2-2 | A wrong invite token returns 403 with no trip details; a non-member asking for a trip gets 404 | Pass |

Also checked: login with a wrong password and with an SQL-injection-style username both return 401; a non-image data URL is refused; every query uses `prepare().bind()`; user text is rendered with `textContent`; no `innerHTML` or `console.log` in the code; a headless browser run of sign-up, create trip, add moment, invite join, and bad invite showed no script errors. One bug was found and fixed in review: the empty photo preview showed as a broken image because a CSS rule overrode the `hidden` attribute.

Giancarlo reviewed every file before committing. Still to verify after deployment: the same EARS checks at the workers.dev URL, and a full-size phone photo (Giancarlo's Prediction Stake).

## Findings

- The draft added a `sessions` table that the first ARCHITECTURE.md schema did not have, because F1-1 says sign-up "shall sign them in." The schema section in ARCHITECTURE.md should list it.
- Invite tokens are stored only as hashes, as the ARCHITECTURE.md schema says, so the app shows the invite link only once, when the trip is created. This meets F2-1 and F2-3 but is a usability cost worth testing with real users.
- Photos are resized in the browser and stored in D1 as data URLs, capped by the Worker. This follows ADR-001's consequences; if real phone photos fail, that is an ADR-002 decision for the Architect.
